定位：把"渐进式操作思路"翻译成可视化的东西

目标用户不是要写脚本的人，而是有一堆一次性、频繁变动的整理需求、又不敢盲操作文件的人。

一次性 + 频繁变动

"这次把下载文件夹里的歌整理一下"——需求每次都不一样，写脚本不划算，改脚本更不划算。搭积木的成本必须低于写脚本。

不敢盲操作

"我点了执行，然后 2000 个文件全乱了"是这类工具最大的恐惧。所以每一步都必须能看见结果，且执行必须可撤销。

要的是过程不是规则表

人的思路是"先筛、再排除、去空格、加序号"，是有顺序的流水线，不是一堆同时生效的规则。规则表的工具表达不了"上一步的输出"。

①

主界面布局

三栏 + 一条读数链。左侧是"我做了什么"，中间是"结果长什么样"，右侧是"这一步怎么配"，底部是"现在还剩下多少"。

四块区域的职责与联动

区域尺寸职责联动规则
A · 积木栈 306px 固定 纵向步骤列表。每张卡片显示：序号、类型图标、名称、本步输出数、参数摘要。支持拖拽排序、禁用（旁路）、复制、删除。数据源固定在首位，不可拖出。 点击任一卡片 → 中栏立刻切到该步的输出；卡片上的数字与状态栏读数链同源。
B · 预览表格 自适应（最小 480px） 当前选中积木的输出。双列对比：原始文件名/路径 → 新文件名/新路径。行按变更类型着色。每行可勾选排除。 参数改动 → 150ms 后重算 → 表格刷新；勾选某行 → 该文件退出后续所有步骤，但仍以"已排除"留在表里。
C · 参数面板 348px 固定 按积木自己声明的 fields 自动渲染表单。模板积木带变量插入按钮 + 实时样例；筛选积木带扩展名 chips。 参数错误（非法正则、未知变量）在面板内即时红字，不等整条栈重算。
D · 状态栏 38px 左侧是读数链（2137 → 560 → 486 → 486 → 486 → 486 → 486），中间是改名/移动/删除/冲突计数，右侧是编译耗时与撤销入口。 读数链上每个数字都是按钮，点它等价于点左侧对应积木。

为什么是"双列对比"而不是单列

用户判断"这一步对不对"，靠的是眼睛扫一眼差异，不是读文字。所以表格必须让"原来叫什么"和"现在会叫什么"同时在场，且中间用一个 → 引导视线。这也是 PowerToys PowerRename 被广泛接受的原因——它把 diff 做成了第一公民。

状态列只回答一个问题：这一行接下来会发生什么。取值只有六种，与行底色一一对应：

改名
文件名变了，位置没变
移动
目录变了（可能同时改名）
删除
进暂存区，可撤销
冲突
目标已存在 / 批内重名，优先级高于前三者
保留
这一步没动它
已排除
不参与后续，但也不会被动
!
一个容易踩的语义坑：被"筛选/排除"积木排除的文件，状态是 excluded（不参与后续，磁盘上原样不动）， 而只有"删除"积木才会把状态置为 deleted（移入暂存区）。两者在表格里颜色不同、在计划里 action 不同， 混为一谈会让"我只是想筛出音频"变成"删掉 1577 个文件"。

积木清单与参数定义

第一版 10 种积木，全部是纯函数。新增一种积木 = 往注册表加一项，界面不用改一行代码。

统一接口

所有积木共用同一个签名，关键在于返回的数组长度恒定——"减少条目"被降级为"改状态"。这是整套设计能成立的地基。

// 积木自己声明表单，UI 不认识任何具体积木
interface StepDefinition<P> {
  type: string;              // 'rename.template' —— 也是项目文件里的 type 字段
  name: string;
  category: 'source' | 'order' | 'filter' | 'transform' | 'output';
  icon: string;
  fields: FieldSpec[];          // 右侧面板据此渲染
  defaults: P;
  validate?: (p: P, ctx: StepContext) => StepIssue[];  // 参数级即时校验
  summary: (p: P) => string;    // 积木卡片上的副标题
  run: (items: readonly FileItem[], p: P, ctx: StepContext, stepId: string) => StepResult;
}

interface StepResult {
  items: FileItem[];        // 长度与输入完全相同
  issues: StepIssue[];
  stats: { total: number; active: number; changed: number; dropped: number };
}
↳
StepContext 里没有 adapter。这是硬约束：一旦 run 能碰磁盘，它就不再是纯函数，实时预览、可测试、可重放这三件事会同时崩掉。 扫描发生在编译入口（边界处）一次，此后全程同步。

变更计划的数据结构

积木栈编译出的唯一产物。执行器只认这个结构，完全不理解积木是什么；反过来，积木也完全不知道磁盘长什么样。

条目模型：一条记录贯穿全程

所有积木都在同一条 FileItem 上工作。origin 只读，永远记录"它原本是什么"；cur 可变，记录"现在它变成什么"。

interface FileItem {
  readonly id: ItemId;        // = pathKey(原绝对路径)，跨重算稳定
  readonly origin: {             // 永不修改
    readonly dir: string; readonly name: string;
    readonly base: string; readonly ext: string;
    readonly size: number; readonly mtimeMs: number;
  };
  cur: { dir: string; name: string; base: string; ext: string; seq: number };
  status: 'active' | 'excluded' | 'deleted';
  deletedBy?: string;         // 被哪一步删除
  excludedBy?: 'manual' | string;  // 手动排除 or 被哪一步筛掉
  touchedBy: string[];          // 哪些步骤真正改动过它（含伪步骤 '__manual__'）
  issues: StepIssue[];
}

为什么删除不摘元素

  • 数组长度恒定 → 行 key 稳定，虚拟滚动不跳行
  • 最终计划 = origin ↔ cur 的纯 diff，不需要逐步累积旁路数据
  • 撤销按 id 定位，不依赖副作用日志反查
  • 被排除的行仍然看得见 —— 用户需要知道"我筛掉了什么"

为什么"用户的决定"不写在 item 上

  • 勾选排除、双击改名，都是用户输入，不是步骤产物
  • 如果写进 item，改一次参数重算就会被冲掉
  • 所以存在 PipelineDoc.excludedIds（排除）和 PipelineDoc.overrides（手改）两张稀疏表
  • 前者作为"第 0 步"的输入参与签名，后者在编译末尾盖最后一层 —— 详见 ④ 节

计划条目

type PlanAction = 'keep' | 'rename' | 'move' | 'copy' | 'delete';

interface PlanEntry {
  itemId: ItemId;
  action: PlanAction;
  from: string;              // 绝对路径
  to: string | null;       // delete 时为 null
  reason: string;            // '去空格 → 模板重命名 → 移动'
  touchedBy: string[];
  overwrite: boolean;         // 策略应用后的结果
  blocked?: string;            // 不可执行的原因（非法名 / 按策略跳过）
  size: number;
}
!
改名 + 移动同时发生时，只产生一条 move，to 里已经含了新名字。 因为落盘就是一次 rename(old, new) 系统调用，拆成两条会凭空造出一个"改了名但还没移走"的中间状态—— 这个状态在磁盘上从未存在过，回滚时却要处理两次。

action 语义表

action判定条件执行动作撤销方式
keep名称与目录都没变，或已被排除/跳过跳过，不产生任何 IO无需撤销
rename目录不变，名称变了同目录 rename()，原子move(to, from)
move目录变了（可能同时改名）同盘 rename()；跨盘 copy + delete逆序 move(to, from)
copy移动积木选了 copy 方式copy(from, to)，原文件保留把副本移入暂存区
delete被删除积木置为 deleted移入 .jianyi/trash/<journalId>/restore(trashPath, from)

冲突检测：两层分工

冲突不能只在一个地方检测，因为两类冲突的反馈时机完全不同：

第一层 · 步骤内（即时）

检测"这一条自己就不合法"：

  • 非法字符 \ / : * ? " < > |
  • 空名、只有扩展名
  • 结尾空格 / 点（Windows）
  • 系统保留名 CON PRN AUX NUL COM1…
  • 超过 255 字节

为什么要即时：这是参数写错了，用户改模板时就该看到红字，不能等整条栈重算完。

第二层 · 编译末尾（全局）

检测"两条之间打架"或"和磁盘打架"：

  • TARGET_EXISTS 目标已存在
  • BATCH_DUPLICATE 批内两条要变成同名
  • CASE_COLLISION 仅大小写不同
  • CASE_ONLY_RENAME a.txt → A.txt（放行）
  • SELF_TARGET 源和目标是同一个路径
  • DISK_FULL 空间不足

为什么必须全局：改名步骤看不到后面的移动步骤会把文件送去哪，"目标已存在"只有拿到终态才判断得出来。

↳
CASE_ONLY_RENAME 必须特判放行。在不区分大小写的磁盘上，a.txt → A.txt 是完全合法的操作， 但按 pathKey 折叠后两者相同，会被误判成"目标已存在"。而首字母大写恰恰是用户最常用的改名方式之一。 执行时用"临时名 → 目标名"两步改名规避。

策略在计划阶段就应用，执行器不参与决策

skip 跳过

降级为 keep，标 blocked。文件保留原名原位。

overwrite 覆盖

置 overwrite: true。执行时先把旧目标移入备份区，撤销能拿回来。

autoRename 自动重命名

追加 (2)、(3)…按计划顺序对"已占用目标集合"去重。

三条理由，说明为什么不能在执行时才决定：

  1. 预演必须是真的。用户点执行前看到的 to，就是最终会写下去的名字。如果执行时才追加 (2)，那张表就是在骗人。
  2. 改策略要能立刻重算预览。切换 skip / overwrite / autoRename 时，表格应该瞬间变化，而不是"执行完才知道"。所以策略是编译参数，不是执行参数。
  3. 执行器要哑。它只按计划落盘，代码量和出错面都小。执行器唯一保留的判断是落盘前再 exists() 一次（TOCTOU 兜底）。

④

状态流转

从"改一个积木"到"撤销回原样"，中间只有一条主链路。所有异步都收敛在编译和落盘两个点上。

状态与事件表

状态进入条件此状态下可发生的事磁盘状态
EMPTY新建流程，只有一个数据源选文件夹、加积木无变化
SOURCED扫描完成，items 就绪首次编译、加积木无变化
PREVIEW至少一个积木且编译完成改任意参数（触发重算）、勾选排除、拖排序、禁用某步、切换冲突策略无变化
CONFIRMING点"一键执行"且 affected > 0看摘要、选策略、勾"故障注入"、取消无变化
EXECUTING确认执行看进度、禁止编辑（frozen）逐条变化
EXECUTED全部落盘成功撤销、关闭已变更
ABORTED某条失败 → 逆序回滚看失败报告、逐条重试回到执行前（或部分）
UNDONE撤销完成重新扫描、继续编辑回到执行前

手动改写：一个盖在所有积木之上的终态覆盖层

积木解决的是"批量规则"，但真实工作里总有那么几个刺头：一个文件名脏到规则写不出来，或者客户点名要某首歌叫别的名字。这时候去改积木参数是错的——改一个参数会影响另外 485 个文件。正确做法是绕开规则，直接在结果上签字。

做法评价原因
加一个"特例"积木不可取积木必须保持纯函数与可复用。特例一旦进积木参数，参数面板会长出"例外列表"这种东西，规则和例外搅在一起，谁也不敢再动
让用户改文件再重扫不可取用户的诉求是"在这个流程里叫这个名字"，不是"去磁盘上改名"。而且重扫会让所有 id 失效，用户之前做的勾选全丢
终态覆盖层（采用）采用不动积木、不动条目，只在编译末尾对指定 id 叠一层补丁。改积木不影响它，它也不影响别人
 
// PipelineDoc 里多一个字段：以 itemId 为键的稀疏表
overrides: Record<ItemId, { name?: string; dir?: string }>

// 编译末尾：所有积木跑完之后，最后一道工序
function applyOverrides(items, overrides) {
  return items.map((it) => {
    const ov = overrides[it.id];
    if (!ov || it.status !== 'active') return it;   // 已被排除/删除的不盖章
    let cur = it.cur;
    if (ov.name) { const s = splitExt(ov.name); cur = { ...cur, name: ov.name, base: s.base, ext: s.ext }; }
    if (ov.dir)  cur = { ...cur, dir: normPath(ov.dir) };
    if (cur === it.cur) return it;                     // 没变就返回原引用，结构共享不破
    return { ...it, cur, touchedBy: [...it.touchedBy, '__manual__'] };
  });
}

四个设计要点：

  • 优先级最高，且只作用于终态。覆盖层在最后一步之后运行，所以它盖过所有积木。反过来说，用户看到的就是最终结果——所见即所得，不会出现"我改的名字又被后面的积木改回去了"这种鬼故事。
  • 不进 stageCache。覆盖层是常数级开销（只遍历 overrides 的键），所以每次编译都重跑一遍，不参与签名 hash。好处是：改了积木导致 id 集合变化时，覆盖层自动跟着新结果走，不需要任何失效逻辑。
  • 与排除/删除互斥。已被筛掉的条目即使有 override 也不生效（status !== 'active' 直接返回）。用户如果先手改再被上游筛掉，改的那笔不算数，但记录保留——把上游参数改回来，手改立刻复活。
  • 可撤销，且可追溯。touchedBy 里记 __manual__ 伪步骤 id，于是"为什么这个名字变了"永远有答案：nameResolver 遇到它返回「手动修改」。预览表的"原因"列、执行日志、失败报告三处都能显示。
!
覆盖层也要过冲突检测。手改的名字同样可能撞上目标目录里已有的文件。它不享受任何特权——照样进变更计划、照样被 TARGET_EXISTS 抓到、照样按用户选的 skip / overwrite / autoRename 处理。唯一不同的是冲突详情里会标注"该条为手动改写"，让用户一眼看出是自己签的字还是积木算的。

交互：在预览表里双击

不做独立编辑弹窗，就在中栏表格里就地编辑——因为用户改名的判断依据是"这一行周围长什么样"，把他拽到一个只剩一个输入框的弹窗里，等于把上下文抽走了。

  • 双击"新文件名"或"目标目录"单元格进入编辑，Enter 提交、Esc 取消、失焦即提交。
  • 只允许在最后一步的预览上编辑。中间步骤是只读的——那是积木的中间态，改了没意义（下一步还会覆盖），徒增困惑。
  • 提交后该行状态列出现紫色「手动」徽标，工具栏出现 手动 N 计数器，点一下可一键清除全部。
  • 空格可见化：首尾空格、连续空格、紧贴扩展名点的空格渲染成橙色 ·。这条是刚需——"改了名字但看起来没变"九成是空格问题。
  • 手改后的名字仍然参与"序号前缀"之外的格式化校验（非法字符、超长、Windows 保留名），非法就红框拒绝提交，不写进 overrides。

三个让增量真正生效的细节

  • 结构共享。未命中条目复用对象引用；数组无变化时返回同一个数组。于是 stageCache[i].items === stageCache[i-1].items 就能整段短路——改一个参数常常一步都不用跑。
  • 行组件按 item 引用 memo。2137 行里只有真正变的几十行重渲染。
  • 不上 Web Worker。最坏 300ms 只出现在"改第一步"，而 Worker 要付 2137 个对象 structuredClone 的成本 + 双向状态同步复杂度。但 core/ 至今不 import 任何 React/DOM，真机阶段（Tauri + 真实 stat + 10 万文件）整块搬进 Worker 零改动。

执行与撤销时序

// 执行：串行、失败即停、每 200 条让出 UI
preflight(plan)                        // 建目录、空间 ≥ 需要 ×1.2、可写探测；不通过直接抛
for (entry of actionable) {
  signal.throwIfAborted()
  if (entry.overwrite && exists(to))  → move(to, backupPath)   // 记 backup
  if (action === 'delete')         → trash(from, trashDir)   // 记 trash，永不真删
  else                            → move(from, to)          // 记 move + crossDevice
  journal.entries.push(entry)        // 每条成功后立刻追加并 flush
  if (done % 200 === 0) await yieldToUI()
}
journal.status = 'completed'

// 失败：逆序回滚
catch (err) {
  const failed = await rollbackJournal(journal.reverse())
  journal.status = failed.length ? 'aborted' : 'rolled-back'
  throw new ExecutionError(err.message, journal)
}
!
回滚必须逆序。链式改名 A→B、B→C 时，正序回滚会把 C 还原成 B，而 B 的还原又要求 B 为空——互相踩。 逆序则是 C→B、B→A，每一步的前置条件都成立。

失败与撤销的三条硬规则

  1. 失败即停，不跳过继续。半成品状态比"少做了几个"更难善后。"继续执行剩余"做成显式按钮，第二版再给。
  2. 回滚失败不重试、不递归。把 journal 标 aborted，落盘 rollback-report.json（每条：成功/失败/当前真实位置），UI 逐条列出并提供"重试此条"。这是唯一诚实的做法。
  3. 删除只进暂存区。路径 <appData>/.jianyi/trash/<journalId>/，不依赖系统回收站 API（三平台行为不一致），自己实现行为一致且必然可撤销。

故障注入实测

八个只有真机上才会暴露的坑

下面每一条都是实际跑出来的，不是预判——浏览器里用内存文件系统时，一个都不会出现。

  • 路径分隔符必须统一成正斜杠。core 全程 normPath()，Rust 侧 fwd() 也转正斜杠并剥掉 \\?\ 前缀。两边不一致的话，Set<string> 查冲突永远查不中，而且不报错——最难查的那类 bug。
  • Windows 会静默吃掉路径结尾的空格和点。CreateFileW 拿到 七里香.mp3␣ 会去找 七里香.mp3，于是文件明明在、exists() 却说没有，执行器报"源文件不存在"。必须用 \\?\ verbatim 前缀关掉这层规范化。而"去空格"积木恰恰就是在处理这类文件，等于必然踩上。
  • 只改大小写的改名在 Windows 上不可靠。MoveFileEx 对同一文件的大小写改名经常静默成功但名字没变，必须走临时名两步。CASE_ONLY_RENAME 恰恰是被允许的操作，很容易漏。
  • 预检不能把"目录还没建"判成"没权限"。第一次执行时目标目录通常不存在，探针文件写不进去就 canWrite = false，用户永远建不出第一个目标目录。正确做法是往上找最近一个存在的祖先再探针。
  • Tauri 的 Err(String) 是以字符串 reject 的，不是 Error。上层到处 (err as Error).message 会拿到 undefined，弹窗上只剩一句"执行中断"，什么原因都看不到。所有 IPC 必须走同一个包装函数统一成 Error。
  • allFilePaths 必须带 scope。传源目录 + 各个输出目录。真机上遍历整块盘会卡死。
  • 没选文件夹时不能让 scanDir('') 抛错。真实模式启动时根目录可能为空，得给一个空数据集 + 引导页，而不是红屏。演示数据也要显式打黄标——它和真磁盘长得一模一样，不标用户会以为自己在改真文件。
  • 关掉执行弹窗不能把撤销入口一起关掉。撤销横幅原本依赖 exec.status === 'done'，一关弹窗状态就变成 idle，横幅跟着消失，用户再也撤不回来。而"可撤销"正是这个工具的核心承诺。改成只要 journal 还在，入口就一直在。

还没做的

  • 崩溃恢复。journal 目前只在内存里。要每条 flush 到 <appData>/journal.jsonl，启动时检测未完成记录并提示恢复。这是断电/强杀后能救回半成品的关键，值得单独做一轮。
  • 把 core 搬进 Worker。core 至今不 import React/DOM，整块搬过去零改动。十万文件级别再考虑。

明确不做（第一版）

不做长期驻留的监控

不做文件监控、不自动触发。那是 Hazel / File Juggler 的领域，本期只做手动触发的一次性批量任务。

不做分支 / DAG

线性栈够用。真要分支，内部把栈编译成 DAG 求值即可，对外仍然只呈现"步骤"，不暴露节点与边。

不做百万级

目标万级以内。当前 2137 × 7 步 ≈ 15ms，余量足够。

不做真删

一律进暂存区，不接系统回收站 API（三平台行为不一致）。执行完提供"清空暂存区"。
